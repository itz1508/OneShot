# OneShot — UI Architecture Gap Review

October 2026 · Market-practice comparison · Design review only

Verdict: The proposed architecture is viable, but it is not yet interaction-complete. The strongest part of the design is the separation between Agent Chat, System Chat, source management, editing, and temporary processing. The main gaps concern transitions between those views, preservation of user work, real-time event behavior, and responsive layout.

The most important correction is that [5] Process Display is a temporary operating mode, not a fifth permanent column.

## 1. Preserve the proposed five-view hierarchy

[1] Agent Chat

Independent agent conversation

[2] System Chat

System-facing context and interaction

[3] Attachments

Import, file tree, selection, Start/Pause

[4] Editor / Review

Inspect, edit, Save, Diff Review

Temporary replacement of [4] only

[5] Process Display

Opened by Start in [3]; event-driven, temporary, disappears when processing ends

The recommended behavior is that starting processing temporarily changes the detail-display slot from Editor/Review to Process Display. It does not reset either chat, discard edits, or rebuild the entire application.

This aligns with Visual Studio Code's customizable, collapsible workbench regions and Claude's contextual artifact editing beside conversations.&#x20;

The crucial separation is that the diagram describes detail-slot state, not navigation across five separate applications.

### Required transition behavior

| Trigger                  | [3] Attachment Drawer        | [4] Editor/Review                | [5] Process Display                         | [1]/[2] Chat                          |
| ------------------------ | ---------------------------- | -------------------------------- | ------------------------------------------- | ------------------------------------- |
| Import source            | Add item to source tree      | Unchanged                        | Hidden                                      | Unchanged                             |
| Click file `[>]`         | Select/expand file           | Opens selected file              | Hidden                                      | Unchanged                             |
| Edit file                | Selection retained           | Editable, dirty state tracked    | Hidden                                      | Unchanged                             |
| Click Start              | Display active source scope  | Visually closes; draft retained  | Opens when start accepted                   | Unchanged                             |
| Processing event arrives | Update relevant source state | Preserved                        | Update active operations                    | Optional minimal system status in [2] |
| Click Pause              | Maintain selection           | Preserved                        | Request pause; show pending until confirmed | Unchanged                             |
| Click Resume             | Maintain selection           | Preserved                        | Continue event display after confirmation   | Unchanged                             |
| Completed                | Show prepared results        | Reopens with previous state      | Closes                                      | No automatic Agent action             |
| Partial/failed           | Mark affected sources        | Reopens with reviewable findings | Closes after terminal state is acknowledged | No invented success message           |

One specific improvement: avoid making [5] a blocking modal by default. A context-sensitive process panel replacing [4] is better aligned with your instruction to leave the chat areas alone. Modal presentation should be reserved for operations genuinely requiring exclusive attention.

## 5. Ephemeral thinking mode — what should actually be dynamic?

Your requirement for thinking mode is better understood as transient presentation of live system activity, not a fixed checklist or an Agent's internal reasoning transcript.

The example intentionally omits fake percentages for Analysis or Normalization. A count of inspected files is a valid measure of file coverage; it is not necessarily a measure of total processing completion.

Carbon's progress guidance explicitly differentiates determinable progress from indeterminate operations.&#x20;

### Live event behavior

The process display should react to actual operation events. The following fields represent information the UI may need, not a proposed mandatory backend JSON schema.

| Event information             | Why the UI needs it                                                |
| ----------------------------- | ------------------------------------------------------------------ |
| Operation identity and source | Associate an update with the correct file or active preparation    |
| Sequence and timestamp        | Order events, reconcile reconnects, and prevent duplicate playback |
| Operation type                | Display the actual activity rather than predetermined phases       |
| Status                        | Distinguish running, completed, failed, or interrupted operations  |
| Counts, if measurable         | Display genuine inspected coverage                                 |
| Result reference              | Open the prepared context or affected file for review              |
| Failure or limitation         | Explain why an item could not be processed                         |

This follows the event and operation-tracing distinctions in OpenTelemetry, where spans represent operations and timestamped events represent occurrences within them.&#x20;

[image](https://www.google.com/s2/favicons?domain=https://opentelemetry.io\&sz=32)

OpenTelemetry



The visual dot, pulse, or loading animation is merely a rendering of that information.

Do not use animation timers to invent Scan, Read, Analysis, or Normalization progress.

## 6. Editor/Review needs a stronger safety boundary

The largest product risk is the transition from editing to processing.

Your design specifies that clicking Start automatically closes the editor. Visually that is reasonable; destroying the editor's state would not be.

A market-aligned correction is to preserve a recoverable working revision. VS Code retains unsaved editing state, while its diff editor distinguishes changes from earlier versions.&#x20;

[image](https://www.google.com/s2/favicons?domain=https://code.visualstudio.com\&sz=32)

code.visualstudio.com

+1



For OneShot, the recommended behavior is:

- Start uses an explicitly determined source snapshot. If unsaved edits exist, their inclusion must be clear.
- Opening [5] hides [4] but does not discard the working revision.
- Completion restores the file and editing position the user was viewing.
- Generated prepared context is displayed as a separate reviewable result.
- Save and Diff Review remain deliberate editing actions, not automatic source mutation.

This preserves your separation between system preparation and user-controlled editing.

## 7. Responsive behavior and accessibility

Atlassian's modern navigation system treats side navigation and contextual panels as independently collapsible and resizable, switching to overlays at smaller viewport widths.&#x20;

[image](https://www.google.com/s2/favicons?domain=https://atlassian.design\&sz=32)

Atlassian Design



For OneShot, the layout could adapt without changing its logical ownership:

| Display          | Recommended presentation                                                                                          |
| ---------------- | ----------------------------------------------------------------------------------------------------------------- |
| Wide desktop     | [1] Agent Chat, [2] System Chat, [3] Attachments, [4/5] active detail slot; user-controlled widths and visibility |
| Standard desktop | Chat remains dominant; auxiliary regions collapse when not needed                                                 |
| Tablet           | One primary conversation with selectable system/source/detail drawers                                             |
| Mobile           | One primary screen at a time, preserving state as views change                                                    |

The `[>]` controls must support keyboard activation and communicate expanded state. Temporary status changes should use non-disruptive accessible announcements. Animations should respect reduced-motion preferences.&#x20;

## 8. Final design assessment

| Design dimension                              | Assessment                                                          |
| --------------------------------------------- | ------------------------------------------------------------------- |
| Separation of Agent and System Chat           | Keep — essential product distinction                                |
| Attachment drawer and hierarchical sources    | Keep — appropriate for multiple and nested files                    |
| Single paperclip import entry                 | Keep — compact and consistent                                       |
| Click file to open Editor/Review              | Keep — supports direct inspection                                   |
| Start swaps Editor/Review for Process Display | Keep, with state preservation                                       |
| Start/Pause and live operation updates        | Needs a verified control contract                                   |
| Ephemeral thinking and event loading          | Keep, driven by real events                                         |
| Save and Diff Review                          | Keep, with non-destructive revision handling                        |
| Automatic return to Editor/Review             | Keep, with defined completion/error behavior                        |
| Four permanently visible equal-width columns  | Reject — allow responsive and collapsible regions                   |
| Permanent workflow graph inside either chat   | Reject — it conflicts with the intended lightweight conversation UI |

Recommended disposition: Accept the modular direction for continued design, but do not treat the interaction specification as implementation-ready until G01–G07, G10, and G11 have defined and testable behavior.

The governing UI model is:

Four independent product zones, one temporary processing view, and one actual system-event stream.

System preparation may be complex internally, but its presentation should remain lightweight, transient, and contextual. Agent Chat and System Chat retain their independent roles while the attachment and review surfaces transition according to user actions.

No repository modifications or design-file changes were made; this is a market-informed review of the supplied reference.
